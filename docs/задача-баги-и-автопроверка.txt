# Задача для Claude Code — автопроверка, баги, разделение кабинетов

*22 июля 2026 · передать целиком в новую/текущую сессию Claude Code*

---

## ЗАДАЧА 0 (сделать первой, до багфиксов) — автоматическая самопроверка после деплоя

Владелец больше не хочет вручную проверять всё скриншотами после каждого деплоя. Нужен скрипт/набор проверок, который Claude Code запускает **сам, автоматически, сразу после деплоя**, без участия владельца:

- Логин под каждой ролью (Владелец/Администратор/Мастер) — проверить, что возвращается 200, а не 401/500.
- `/api/health` — проверить статус ok.
- Базовые GET-запросы по ключевым разделам (безопасность, дедлайны, журналы, финансы, склад, поддержка) — проверить, что не возвращают 500/пустой ответ там, где должны быть данные.
- Если что-то из этого падает — Claude Code должен **сам** это обнаружить и сообщить владельцу словами "автопроверка после деплоя нашла проблему в X", а не ждать, пока владелец наткнётся на баг руками.

Раз в 45-90 дней подобные баги теряют часы времени владельца именно потому, что проверка ручная. Эту задачу считать инфраструктурной и постоянной — не разовой.

## ЗАДАЧА 1 (ОБСУДИТЬ ДО НАЧАЛА БАГФИКСОВ) — разделение "Кабинет владельца" и "Кабинет клиента"

**Проблема:** сейчас один интерфейс пытается быть одновременно и панелью управления для владельца бизнеса (данные, настройки, финансы, склад), и рабочим экраном для мастера/администратора студии. Это создаёт путаницу и, вероятно, часть багов из списка ниже — потому что логика двух разных пользовательских задач смешана в одном UI.

**УТОЧНЕНИЕ (важно!):** речь не о разделении ролей внутри клиентского кабинета (Владелец студии/Администратор/Мастер — это всё остаётся как есть, это одна система). Речь о **втором, полностью отдельном уровне** — кабинете владельца ВСЕЙ ПЛАТФОРМЫ (Артёма), которого сейчас просто не существует. Сейчас есть только клиентский кабинет (то, что видит любая подписавшаяся студия). Нужно добавить отдельный кабинет для управления самим бизнесом "Безопасный бизнес" — всеми студиями-клиентами, подписками, метриками роста.

**Принятое архитектурное решение (согласовано с владельцем):**
- Отдельный адрес, например `admin.<домен>` — полностью отдельное фронтенд-приложение, недоступное клиентам ни при каких обстоятельствах.
- **Тот же сервер и та же база данных** — отдельный сервер не покупается. Это просто второй фронтенд, который обращается к тому же API.
- На backend — отдельная роль/проверка доступа (например `platform_owner`), которая не пересекается с ролями Владелец/Администратор/Мастер внутри клиентского кабинета. Даже если кто-то узнает адрес `admin.<домен>`, без этой роли доступа не будет.
- Такое разделение стандартно и не создаёт технического долга — наоборот, именно оно позволит клиентскому кабинету и кабинету платформы расти дальше независимо друг от друга.

**Что должен показывать кабинет платформы (первая версия, минимум):**
- Список всех компаний-клиентов, дата регистрации, статус подписки (пробный период / оплачено / отток).
- Базовые метрики роста: новые регистрации, активные за 7 дней, конверсия из пробного в оплату (см. раздел 6 бизнес-плана).
- Возможность посмотреть детали конкретной компании-клиента при необходимости (например, для поддержки).

**Порядок действий:** Claude Code — сначала показать владельцу мокап/схему навигации кабинета платформы на согласование, только потом приступать к реализации. Не делать это одним большим пакетом на несколько этапов сразу — начать с минимального списка компаний + базовых метрик, остальное добавлять по мере необходимости.

## ЗАДАЧА 2 — список багов (приоритизировано)

### Критично — ломает базовую работу приложения
1. **Белый экран при навигации.** При переходе в раздел — белый экран, помогает только свайп вверх для обновления. В PWA (иконка на главном экране телефона) — белый экран без возможности обновить вообще, кроме главной страницы. Похоже на проблему роутинга/service worker в PWA-режиме — разобраться в первую очередь, это блокирует использование продукта.
2. **Журналы: показывается только 3 из 5 загруженных**, между тремя нет переключения, не найдено, где их скачать.
3. **Поддержка:** отправленное сообщение не отображается в интерфейсе после отправки.
4. **Приглашение сотрудника:** при указанном email всё равно требует ввод "первого" email вместо уже заданного — логика приглашения сломана.
5. **Ссылки в сообщениях не открываются напрямую** — работают только через копирование в браузер вручную.

### Важно — нелогичное поведение, влияет на доверие к данным
6. **Раздел "Безопасность": процент не пересчитывается** после отметки нарушения как устранённого.
7. **"Мои сроки": поле ввода даты визуально смещено** за пределы своего поля.
8. **Аренда: нет стандартного варианта "11 месяцев"** при выборе срока договора (это самый частый вариант в РФ).
9. **Календарь дедлайнов: нет переключения разделов/видов.**
10. **Финансы: не переключаются периоды** (сегодня / прошлый месяц / произвольные даты).
11. **Приглашения: нет кнопки "поделиться" рядом с пригласительной ссылкой.**

### Нелогичный UX (мешает, но не ломает)
12. **Главный экран не продуман** — нужно отдельно пересобрать (вероятно, решится вместе с Задачей 1).
13. **"Мои сроки": непонятно, зачем в этом разделе дата регистрации ИП и галочка "есть ли наёмные сотрудники"** — если это нужно для автоматического расчёта фиксированных сроков (было решено ранее), нужно явно объяснить это пользователю в интерфейсе (подсказка/тултип), иначе выглядит как нелогичный вопрос не по теме.
14. **Склад → Бар → Добавить: пример в поле названия ("гель лак") не подходит для категории "Бар"** (там, например, кофе) — примеры должны зависеть от выбранной категории. Галочка "дезинфицирующее средство" в контексте "Бар" нелогична — вероятно, это поле должно появляться только для релевантных категорий склада.
15. **"Безопасность" дублируется в разделе "Ещё"**, хотя уже есть в нижней навигации — убрать дубль.

## Как владельцу использовать этот файл
Отдать целиком новой/текущей сессии Claude Code. Начать с Задачи 0 (автопроверка) и обсуждения Задачи 1 (разделение кабинетов) — прежде чем чинить баги 12-15, которые могут измениться вместе с разделением интерфейсов. Баги 1-11 можно чинить параллельно, они не зависят от архитектурного решения.
