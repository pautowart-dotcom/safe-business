## 1. Новый агент — мониторинг актуальности законодательных данных

Владелец подтвердил: нужен агент по образцу `security-reviewer`/`legal-reviewer`, но с другой
задачей — не сверять оферту с кодом, а следить, что сами данные, на которых строится продукт (сроки,
чек-листы), не устарели относительно реального закона.

Это НЕ с нуля — есть черновик-планирование от 31.07:
`docs/law-monitoring-engine/01_Overview_and_Sources.md` (источники: ГАРАНТ.РУ «Горячие документы»,
API Госдумы, платные агрегаторы ПравоДанные/Юрайт — цены и лимиты не проверялись на практике).

**Решение владельца по открытым вопросам того черновика:**
- Область мониторинга — **всё сразу**, не по частям: налоговые сроки (`backend/src/core/taxDeadlines.js`,
  `backend/src/core/deadlines.js`) И санитарные/лицензионные требования
  (`backend/src/modules/security/content/*`).
- Режим — **только предложение изменений владельцу**, никогда не публикует сам. Ошибка в
  комплаенс-данных бьёт реальным штрафом по реальному клиенту, поэтому автопубликация без
  подтверждения человеком не рассматривается.

**Что сделать:**
1. Создать `.claude/agents/law-compliance-monitor.md` (или похожее имя) по формату существующих
   `legal-reviewer.md`/`security-reviewer.md` — frontmatter с `name`/`description`/`tools` (нужен
   `WebSearch`/`WebFetch` в дополнение к Read/Grep/Glob, т.к. агент сверяется с внешними источниками
   закона, не только с кодом).
2. В инструкции агента явно прописать: ищет расхождения между `taxDeadlines.js` /
   `deadlines.js` / `modules/security/content/*` и актуальными нормами (начать с бесплатных
   источников — ГАРАНТ.РУ, Госдума — платные агрегаторы не подключать без отдельного решения
   владельца о бюджете); каждая находка — с конкретной ссылкой на источник, что именно устарело и
   что рекомендуется поменять; НЕ переписывает данные сам, только список находок владельцу.
3. Явно указать агенту его ограничение: он не замена настоящему юристу при реальном споре,
   а сигнализация о возможных изменениях — снижает риск того, что что-то устареет незамеченным, но
   не гарантирует юридическую точность интерпретации.
4. Первый прогон — по всей области сразу (налоги + санитарка/лицензии), результат — список находок
   владельцу на решение, ничего не менять в чек-листах автоматически.

## 2. Аналитика в admin-frontend

Три уровня, граница между ними определяется уже действующей политикой конфиденциальности
(`backend/src/db/migrations/0013_legal_documents.sql`, §6, §8, §10) — ничего нового в законе
придумывать не нужно, она уже это разрешает/запрещает явно.

### А. Внутренняя бизнес-аналитика (без ограничений — операторские данные)

Новая страница в `admin-frontend/src/pages/` (сейчас там `Overview.jsx`, `Companies.jsx`,
`JournalTypes.jsx`, `LegalDocs.jsx`, `Support.jsx`, `ClientErrors.jsx` — аналитики как таковой ещё
нет). Метрики:
- выручка по компаниям, MRR;
- конверсия триал → оплата;
- retention/удержание, активность по компаниям;
- какие пункты чек-листа/аудита безопасности чаще всего проваливаются — **в целом по базе**, без
  привязки к конкретной компании в самом дашборде для владельца сервиса (это уже продуктовая
  метрика, не персональные данные компании).

### Б. Продаваемая агрегированная статистика (фаза 2, после А)

Разрешена политикой §10.1–10.3: обезличенные агрегированные данные, не позволяющие вычислить
конкретную компанию/человека, для аналитики/исследований рынка/отраслевой статистики.

Уже частично построено: поле `analytics_consent` в таблице `users` есть с 0013-й миграции, чекбокс
уже стоит в `frontend/src/pages/AcceptInvite.jsx`, `Login.jsx`, `Settings.jsx` (отдельно от акцепта
оферты, как требует §10.3). Сам флаг сейчас нигде не используется дальше сбора.

**Что построить:**
- Логика агрегации: считать статистику только по компаниям с `analytics_consent = true`.
- Порог анонимности: не отдавать/не показывать срез, если группа меньше N компаний (иначе
  конкретную компанию можно вычислить по контексту — например «единственная студия в этом районе»).
  Конкретное число N — решить с владельцем, не выдумывать самостоятельно.
- **До реализации** — прогнать саму механику агрегации (не готовые данные, а именно алгоритм и
  порог) через `legal-reviewer`, чтобы подтвердить соответствие §10.2 (запрет обратной
  идентификации).

### В. Жёсткая красная линия — никогда не продавать и не агрегировать

- Данные аудита безопасности отдельных компаний (§8 политики — «наиболее чувствительная
  категория», шифрование, доступ только у владельца компании, не передаётся третьим лицам).
- Любые идентифицируемые данные клиентов студий (телефон, визиты, предпочтения/аллергии).
- См. пункт 3 ниже — реальная выручка (включая наличные) относится сюда же, не в категорию Б.

## 3. Способ оплаты визита

Владелец попросил добавить поле «способ оплаты» (наличные/карта/перевод и т.п.) к визиту —
по образцу того, как сейчас мастера/админы студий сами репортят это в Telegram-отчётах.

**Кто вводит vs кто видит сводную выручку — это разные вопросы, владелец явно развёл их:**
- **Ввод поля при визите** — открыт тем же ролям, что и сейчас могут создавать/редактировать визит
  (проверено: `backend/src/modules/visits/visits.routes.js`, роуты создания/правки визита сейчас
  без `requireRole` — доступны любому сотруднику компании, не только владельцу). Логично, что
  способ оплаты вводит тот же человек, что и сам визит — обычно мастер/админ, не владелец лично.
- **Просмотр сводной выручки по способам оплаты** (отчёты/дашборд с разбивкой нал/карта/перевод) —
  вот здесь и применяется ограничение ниже, не к самому полю ввода.

**Технически:**
- Новая колонка в таблице `visits` (миграция по образцу существующих в `backend/src/db/migrations/`,
  сейчас там нет такого поля — проверено, `payment_method` в БД пока используется только для
  `yookassa_payment_method_id` подписки компании, это другая сущность).
- Поле в форме визита (`frontend/src/pages/Visits.jsx` и связанные компоненты) — доступно всем
  ролям, вводящим визит.
- Разбивка выручки по способу оплаты в финансовых отчётах (`backend/src/modules/finance/`) —
  сама разбивка/сводный отчёт с фильтром по способу оплаты и итогами по нему — только роль
  «владелец» (по аналогии с тем, как уже скрыта итоговая чистая прибыль от admin/master, см.
  `risks.md`/`legal-reviewer.md` §5). Мастер/админ видит и вводит способ оплаты в самом визите (это
  нужно для работы), но не видит агрегированную выручку по нему за период.

**Важная пометка (моя рекомендация по downstream-использованию, не решение владельца — на
подтверждение):**
Эти данные раскрывают реальную выручку студии, включая наличные, которые не видны банку/налоговой —
владелец сам это и назвал главной ценностью. Именно поэтому агрегированная сводная сумма особенно
чувствительна. Рекомендация: относиться к сводной выручке по способам оплаты не менее строго, чем к
данным аудита безопасности (§8 политики) на уровне ПРОСМОТРА СВОДКИ — и жёстко исключить из
категории Б (никогда не участвует в агрегированной/продаваемой межкомпанийной статистике, даже
обезличенной). Ввод самого поля в визите — не ограничен, это разные уровни.
