# Статус на 04.08.2026 — передача в новый чат

Продолжение `docs/status-2026-07-31-handoff.md`. Сессия 31.07–04.08, очень длинная и продуктивная — сначала закрыли главный блокер (сайт не открывался у реальных пользователей в России), потом прошлись по чек-листу мелких багов и фич из практического использования.

## Главное: сайт снова не грузился у пользователей в России — теперь решено, причина другая

Хендофф 07-31 оставил гипотезу "поддомен `lk.business-safe.ru` блокируется по SNI" и план — перейти на пути (`business-safe.ru/lk/`) вместо поддоменов. План выполнили полностью, но **сама гипотеза оказалась неверной/неполной** — после переезда на пути ничего не изменилось, сайт всё ещё не открывался ни на одном операторе (МТС/Билайн/Мегафон), включая домашний интернет.

Реальная причина нашлась в два шага:

1. **DNS домена всё ещё шёл через Cloudflare**, хотя проксирование (оранжевое облако) отключили ещё 31.07. NS-серверы (`hadlee.ns.cloudflare.com` / `jarred.ns.cloudflare.com`) остались на Cloudflare — а именно инфраструктуру Cloudflare (не только прокси, но и её вообще) блокируют/тормозят российские провайдеры. **Исправлено**: DNS полностью перенесён на `ns1.reg.ru`/`ns2.reg.ru` (все записи — A/MX/SPF/DKIM/DMARC — перенесены вручную, сверены построчно с Cloudflare перед переключением). Cloudflare теперь нигде не участвует.
2. Даже после этого сайт всё ещё зависал у части пользователей. Нашли вторую, куда более конкретную причину: **с июня 2026 ТСПУ РКН блокирует клиента на 120 секунд за много TLS-соединений подряд** — HTTP/1.1 открывает по 6+ параллельных соединений на страницу (по одному на файл), это интерпретируется как туннелирование/DDoS. Лендинг (один файл) под порог не попадал, страница входа/визитов (JS-бандл + CSS + несколько API-запросов) — попадала. **Исправлено**: включили HTTP/2 в nginx (`listen 443 ssl http2`) — браузер использует одно TLS-соединение вместо десятков.

**Владелец подтвердил: сайт заработал** после этих двух исправлений.

### Побочные находки/фиксы по ходу этого расследования
- Второй (лишний) floating IP на сервере Timeweb (`104.171.137.253`, платный) — отвязан и удалён, остался только рабочий `89.23.100.252`.
- При отвязке IP сервер неожиданно перезагрузился — обнаружили, что **PM2 не был настроен на автозапуск после ребута** (после перезагрузки сайт не поднимался сам, backend стоял, `502` на `/api/*`). Настроили `pm2 startup` + `pm2 save` — теперь переживёт любую перезагрузку.
- Задвоение `/lk/lk/...` в ссылках-приглашениях и QR-кодах журналов — баг, внесённый в процессе миграции на пути (см. коммит `a622e73`). Уже исправлено, но **старые ссылки-приглашения, отправленные до фикса, остались битыми** — если кто-то жалуется на белый экран по старой ссылке, нужно перевыпустить приглашение.

## Все остальные правки этой сессии (после того как сайт заработал)

Шли по списку мелких проблем, которые владелец находил при живом тестировании:

1. **Визит не сохранялся, если не выбран мастер** — раньше валидация была только нативная браузерная (`required`), на длинной форме подсказка браузера легко оставалась не на виду. Теперь явная проверка с понятной ошибкой наверху формы.
2. **`operator is not unique: unknown * unknown`** при сохранении визита — SQL-баг (умножение двух непривязанных к типу параметров в запросе к `finance_entries`), поправлен явным `::numeric`.
3. **Финансы считались "по дням"** — постоянные расходы (аренда и т.п., вводятся в ₽/мес) делились на 30 и умножались на число дней в периоде; на "Сегодня"/"Неделя" это выглядело как случайные, ничем не объяснённые числа. Теперь считаются **целиком**, но только на периодах "Месяц"/"Прошлый месяц"; на более коротких периодах — не участвуют в расчёте прибыли вообще (сами записи по-прежнему видны и редактируются).
4. **Автосписание расходника по норме на клиента** — у расходника (склад) можно задать "расход на клиента" (например, 15 мл геля). В форме нового визита такие расходники показаны кнопками-подсказками ("+ Гель-лак №47 · 15 мл") — мастер сам нажимает на использованный, а не всё автоматически (иначе списались бы все нормированные расходники сразу, включая неиспользованные).
5. **Приход расходников по таре, не по 1 шт.** — у расходника можно задать "объём одной тары" (например, 500 мл); кнопки "Пришло"/"Списать" теперь открывают поле количества (для "Пришло" предзаполнено объёмом тары), а не сразу меняют остаток на 1.
6. **Удаление расходника "не работало"** — на самом деле работало правило (нельзя удалить, если уже использован в визитах), но ошибка нигде не показывалась — `handleDelete` не ловил исключение. Теперь показывает `alert()` с причиной.
7. **"Неверный код" при входе, хотя вход уже произошёл** — проверка "уже залогинен → перенаправить" в `Login.jsx` шла ПОСЛЕ проверки "показать экран кода". Если код по факту был принят (гоночная ситуация с двойной отправкой), экран кода всё равно оставался с последней ошибкой. Поменяли порядок проверок.
8. **Пожелания/аллергии клиента не видны в визите** — данные в карточке клиента уже были (`preferences`/`allergies`), просто нигде не показывались при поиске/выборе клиента в форме визита. Добавлено.
9. **Поиск клиента только по имени/фамилии** — добавлен поиск и по телефону (сравнение по цифрам, разные форматы номера считаются одним).
10. **Дубликаты клиентов по телефону** — раньше ничего не мешало завести двух клиентов с одинаковым номером. Теперь при совпадении сервер переспрашивает ("это точно другой человек?"), не блокирует жёстко (номер иногда реально общий, например у пары).
11. **"+ Добавить студию" не проверял роль** — теоретически админ/мастер мог создать свою отдельную компанию через экран "Сменить компанию". Заблокировано на бэкенде (только owner) и скрыто на фронтенде для остальных ролей.
12. **Аватар в личном кабинете — битая картинка** — забытый хвост security-аудита 29.07: тогда подписали ссылки на визитные фото/документы короткоживущей подписью, но аватар сознательно не тронули ("низкая чувствительность"), а сама раздача `/api/uploads` стала требовать подпись у ЛЮБОГО файла без исключений. Аватар с 29.07 отдавал неподписанную ссылку, которую сервер сам же отклонял (403). Починено во всех точках, где отдаётся `avatar_url` (`requireAuth` middleware, login, verify-code, accept-invite, `/me/avatar`).

13. **Фото в визите — только "сделать сейчас"** — у поля загрузки фото стоял `capture="environment"`, из-за чего на мобильном браузер сразу открывал камеру, без выбора "из галереи". Добавлена вторая кнопка (иконка "галерея" рядом с "камера") — выбор существующего файла без `capture`. Не задеплоено вместе с остальным (фронтенд-фикс, требует обычного передеплоя).

Также по ходу разбора многокомпанийности объяснили владельцу: "Сменить компанию" в Настройках уже работает для любой роли (не только владельца), просто нужно пригласить одного и того же человека в обе студии отдельно. Отдельная роль "управляющий" пока не нужна — админ уже имеет почти все права владельца внутри одной компании; смысл добавлять её появится, только если понадобится **сводный** вид по нескольким студиям сразу (это отдельная, более крупная функция, которую сознательно не стали строить сейчас).

## Деплой — проверено 04.08, актуален

Сверились в начале сессии 04.08: реальные файлы на сервере соответствуют `3a67571` (последний коммит на тот момент) — проверено не по git-логу (см. ниже, почему ему нельзя верить), а по содержимому: в `auth.routes.js` есть фикс подписи `avatar_url`, в `nginx.conf` есть `listen 443 ssl http2`, время изменения файла (`2026-08-02 11:44:40 UTC`) совпадает с моментом коммита `3a67571`.

**Важно: `git log -1` на сервере (`/var/www/safe-business`) показывает старьё и НЕ годится для проверки версии.** Деплой-скрипт клонирует репозиторий во временную папку, удаляет там `.git` и копирует файлы через `cp -r` поверх `/var/www/safe-business` — сама папка `.git` в боевой директории осталась от какого-то старого способа разворачивания (когда деплоили прямым `git clone` на месте) и с тех пор не обновляется, хотя файлы обновляются исправно. На 04.08 она показывала `7d96e61` (коммит от 24.07), хотя на диске реально лежал код от 02.08.

**Как проверять деплой правильно** (не git log):
```bash
# конкретная строка кода из последнего коммита — есть ли она на диске
grep -n '<уникальная строка из свежего коммита>' /var/www/safe-business/<путь к файлу>
# время реального изменения файла
ls -la --time-style=full-iso /var/www/safe-business/<путь к файлу>
```
Сравнить время с `git show <hash> --format=%cd --date=iso-strict` локально.

Команда деплоя (если понадобится передеплоить):
```bash
cd /tmp && rm -rf safe-business-src && git clone https://github.com/pautowart-dotcom/safe-business.git safe-business-src && rm -rf safe-business-src/.git && cp -r safe-business-src/. /var/www/safe-business/ && cd /var/www/safe-business && bash deploy/deploy.sh
```
После неё: `pm2 status` — `safe-business-api` должен быть `online`.
